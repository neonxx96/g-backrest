# Промпт для Antigravity: ночной автотест приложения и баг-репорт

Использовать так: вечером (за 20-30 минут до сна) отправь промпт ниже Antigravity. Он напишет и запустит скрипт, который проработает несколько часов без участия модели, а к утру будет готов `RAW_REPORT.md` с находками. Утром попроси Antigravity (или Cline на дешёвой модели) превратить его в `BUG_REPORT.md`.

---

```
Роль: QA-инженер проекта slab_terminal. Задача: автоматически
"поклацать как пользователь" и проверить приложение на ошибки, а к
утру выдать баг-репорт с замечаниями и предложениями. Основную работу
делает скрипт на Playwright (без вызовов модели), модель нужна только
для написания скрипта и итогового разбора. Так экономятся лимиты.

=== ШАГ 0. ВХОД В КУРС И ИЗОЛЯЦИЯ ===
Прочитай: AGENTS.md, context/LEAD_RULES.md, design/DESIGN_PRINCIPLES.md,
design/ADDENDUM_01_REFERENCES_AND_PRESETS.md, HANDOFF.md, PROGRESS.md,
context/COORDINATION_STATE.json. Если activeAgent равен codex и Codex
сейчас работает в основной папке, это нормально: ты работаешь в
отдельной копии и ничего в основной папке не меняешь.

Основная папка D:\AI_agent_space\gemini принадлежит другому агенту:
только чтение. Запрещено: git clean, git reset --hard, git restore .,
git stash, переключение веток в основной папке, удаление файлов.

1. В основной папке (только чтение): git branch --show-current,
   git log --oneline -3, git status --short. Запиши ветку и хэш в отчёт:
   ты тестируешь именно этот коммит.
2. Создай отдельную рабочую копию:
   git worktree add D:\AI_agent_space\gemini-qa -b agent/antigravity/qa <текущий коммит>
   (если уже есть, используй существующую).
3. Скопируй в копию БД как тестовую: data\signals.db в
   D:\AI_agent_space\gemini-qa\data\signals_qa.db. Тестируй только на
   копии, настоящую БД не трогать.
4. Порты QA-копии: backend 8100, frontend 5180 (основные 8000/5173 могут
   быть заняты). Это единственное допустимое исключение из правила
   портов. Проверь, что адрес бэкенда во фронтенде берётся из настроек
   (env/конфиг), а не зашит. Если зашит, сделай минимальную правку только
   в QA-копии и запиши её в отчёт.
5. Переменные окружения QA-копии: OPENROUTER_API_KEY и TELEGRAM_BOT_TOKEN
   пустые (тест не должен тратить деньги и слать сообщения), DATABASE_URL
   на signals_qa.db. .env основной папки не читать и не печатать.
6. Создай run_qa.ps1: запускает backend и frontend QA-копии на этих портах.

=== ШАГ 1. ЗАЩИТА ОТ ПОБОЧНЫХ ЭФФЕКТОВ ===
- Playwright route: разрешить только localhost (порты QA) и публичные
  источники данных, которые использует приложение (Binance fapi, fstream,
  api, CoinGecko). Все остальные домены блокировать и считать в отчёте.
- Лимит нагрузки на биржу: не более 30 действий в минуту суммарно,
  пауза 3 секунды между запусками бэктеста. При ответах 418 или 429
  остановить все обращения к бирже на 10 минут и записать событие в отчёт
  (риск бана IP).
- Не открывать внешние ссылки и новые вкладки за пределы приложения.
- Реальной торговли в приложении нет; тем не менее скрипт не должен
  нажимать кнопки, которые отправляют данные вовне.

=== ШАГ 2. СКРИПТ scripts/qa/qa_run.py (в QA-копии) ===
Один запуск проходит несколько фаз и пишет результаты в
context/qa/RUN_<дата-время>/ . Параметры: --hours (по умолчанию 6),
--seed (по умолчанию случайный, записывается), --max-actions-per-min.
Все действия логируются в actions.jsonl так, чтобы любую ошибку можно
было воспроизвести командой --replay.

ФАЗА A. Сценарии (детерминированные, 30-45 минут):
по каждому основному экрану один сценарий "как пользователь":
- смена символа (BTCUSDT, ETHUSDT, SOLUSDT и ещё 3 монеты) и таймфрейма
  (1m, 15m, 30m, 45m, 1h, 4h, 6h): заголовок графика совпадает с выбором;
- запуск бэктеста в 1 клик и из панели; все стратегии из
  GET /api/backtest/strategies; Live-Only стратегии помечены;
- Risk/Reward Box и "Тест сетапа"; сортировка и экспорт CSV таблицы сделок;
- слои графика, подвалы CVD и RSI/OI, конус волатильности, цветовые связи,
  док-панели (перетаскивание, свёртывание, ресайз), сохранение раскладки;
- симулятор Live Paper: запуск, остановка, смена баланса и риска;
- журнал решений [J]: ручные действия, фильтры, экспорт CSV;
- пресеты параметров: применить, сохранить, повторно применить;
- AI Copilot и "Мнение AI" при отсутствии ключа: должно быть честное
  "AI недоступен", без выдуманных ответов;
- перезагрузка страницы после каждого сценария: состояние восстанавливается.

ФАЗА B. Перебор параметров через API (около 60 минут):
POST /api/backtest/run с сеткой значений: SL и TP (0.01% до 50%, в том
числе нули, отрицательные, строки, экстремумы), плечо (1, 5, 25, 125),
days (0, 1, 3, 14, 30, 365), комиссии и проскальзывание, min wall,
все режимы входа и стопа, все TF. Проверять:
- нет ответов 500 на корректный ввод; на некорректный 4xx с понятным
  сообщением; нет зависаний дольше 60 секунд;
- детерминизм: один и тот же запрос дважды даёт идентичный результат;
- монотонность: рост комиссий не увеличивает Net PnL;
- согласованность: Net = Gross - комиссии - проскальзывание для каждой
  сделки и в сумме; win rate в 0-100; число сделок в ответе = длине списка;
- пустые данные (мало свечей) дают явную ошибку, а не числа;
- пороги значимости и Verdict согласованы с метриками (отрицательный Net
  PnL не даёт зелёный вердикт).
Записать все нарушения с точными запросами.

ФАЗА C. Случайный обход интерфейса (основная, оставшееся время, 4-6 часов):
- Случайный, но управляемый seed обход: находит интерактивные элементы
  (button, role=button, input, select, слайдеры, вкладки, чекбоксы,
  меню, горячие клавиши), кликает, вводит значения (валидные, на границах,
  невалидные, очень длинные строки, эмодзи, строки вида ' OR 1=1 --,
  <img src=x onerror=alert(1)>), меняет пресеты, размеры окна (1280x720,
  1920x1080, 2560x1440 и узкое), быстро переключает символ и TF.
- Периодически (каждые 5 минут): снимок JS Heap после сборки мусора,
  скриншот состояния, проверка инвариантов, запись в perf.csv.
- Каждые 30-40 минут имитация обрыва сети на 10 секунд (context.set_offline)
  и проверка, что WebSocket-потоки восстановились и интерфейс не показывает
  фейковые числа ("disconnected" или "No data" вместо данных).
- Каждые 60 минут полная перезагрузка страницы и очистка localStorage
  с проверкой, что приложение стартует чисто.
- Сторожевой режим: если страница упала или завис, сохранить скриншот и
  лог, перезапустить браузер и продолжить; если упал бэкенд, записать
  событие, перезапустить его и продолжить (не более 5 раз).

ИНВАРИАНТЫ (проверяются во всех фазах, каждое нарушение это находка):
- На экране нет текста NaN, undefined, null, Infinity, [object Object].
- Нет необработанных исключений JS, unhandled promise rejection, ошибок
  React (error boundary), ошибок в консоли (кроме заранее известных,
  их список вынеси в файл).
- Нет неудавшихся сетевых запросов к бэкенду (4xx/5xx), кроме ожидаемых
  при невалидном вводе.
- Числа согласованы: сделки на графике = в таблице = в CSV; Net PnL в
  плашке = сумма по таблице; Verdict согласован с метриками.
- Нет выдуманных данных: при ошибке API или обрыве сети UI показывает
  No data или disconnected, а не числа по умолчанию.
- Нет Math.random() в значениях, видимых пользователю (проверь поиском по
  исходникам frontend/src и перечисли места).
- Цвета интерфейса и состояния соответствуют design/ (No data, blocked,
  Verdict), нет хардкода цветов вне токенов (поиск по исходникам).
- Поля ввода не дают сохранить заведомо невалидные значения (отрицательные
  SL/TP, нулевые периоды).
- HTML-инъекции из заметок журнала экранируются.
- Стабильность: рост JS Heap за всё время не более заданного порога
  (определи по первому часу), нет роста числа WebSocket-соединений и
  таймеров.
- Задержки: время ответа бэкенда и время перерисовки графика (p50/p95).

Если нужен новый пакет (например, для проверки доступности), используй
только то, что уже есть в проекте, или встроенные возможности Playwright
(accessibility snapshot). Новые пакеты не ставить без моего согласия.

ВЫХОД скрипта (генерируется автоматически, без модели):
context/qa/RUN_<дата-время>/
  RAW_REPORT.md   - сводка: тестируемый коммит и ветка, длительность,

  findings.json   - каждая находка: id, тяжесть (blocker, major,

                    воспроизведения (из actions.jsonl), ожидаемое и

                    контрольных раз в час

=== ШАГ 3. ЗАПУСК ===
1. Сначала короткий пробный прогон (--hours 0.2), проверь, что все фазы
   работают, отчёт формируется, бэкенд и фронтенд стартуют и останавливаются.
   Исправь ошибки в самом скрипте.
2. Затем запусти основной прогон на 7 часов отдельным процессом в
   фоне (Start-Process, вывод в файл), не привязанным к окну агента, чтобы
   прогон продолжился, даже если сессия агента завершится.
3. Напиши в отчёт команду остановки и команду проверки состояния
   (ожидаемое время завершения, число действий, последние находки).
4. После запуска не опрашивай процесс чаще раза в час и не трать токены
   на ожидание.
5. Коммит в ветке agent/antigravity/qa: только скрипты, run_qa.ps1,
   тестовые настройки. context/qa/RUN_* в .gitignore. Обнови
   context/DESIGN_STATUS.md или QA_STATUS.md: что запущено, когда
   завершится, где результаты.
```
