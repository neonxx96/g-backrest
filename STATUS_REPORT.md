## 1. Стек и архитектура

### Фронтенд
* **Фреймворк:** React 19 (`19.2.0`), Vite (`8.3.4`), Tailwind CSS (`4.1.18`).
* **Графический движок:** [klinecharts](https://klinecharts.com/) версии `9.8.12` (HTML5 Canvas-движок с поддержкой аппаратного ускорения, кастомных индикаторов и кастомных оверлеев). Для стакана L2 и таблиц используется нативный DOM/Flexbox/CSS с виртуализацией высоты строк.
* **Стейт-менеджер:** Локальный компонентный стейт React (`useState`, `useRef`, `useCallback`, `useMemo`), синхронизация настроек через REST API и сохранение интерфейсных пресетов в `localStorage` (`panel_orderbook`, `panel_signals`, `terminal_sidebar_width`, `signalscript_theme`). Глобальные шины событий для горячих клавиш через `window.dispatchEvent(new CustomEvent(...))`.
* **PWA:** Поддержка прогрессивного веб-приложения (`manifest.json`, Service Worker `sw.js`, standalone-режим, иконки 192x192 и 512x512).

### Бэкенд и сбор данных
* **Язык и фреймворк:** Python 3.11+, FastAPI (`0.115.0`), Uvicorn (`0.30.0`), Pydantic v2.
* **Подключение к биржам:**
  * **Binance Futures (основной источник):**
    * *WebSocket (real-time):* `wss://fstream.binance.com/ws/!forceOrder@arr` (ликвидации рынка в реальном времени), `wss://fstream.binance.com/ws/{symbol}@depth20@100ms` (L2 стакан со скоростью 100 мс), `wss://fstream.binance.com/ws/{symbol}@aggTrade` (агрегированные тики сделок).
    * *REST API (история и сканирование):* Binance Futures REST v1 (`/fapi/v1/klines`, `/fapi/v1/depth`, `/fapi/v1/ticker/24hr`, `/fapi/v1/openInterestHist`) через `aiohttp` / `httpx`.
  * **Bybit (модуль расширения):** `BybitAdapter` в `backend/app/adapters/exchange/bybit.py` (реализованы REST-методы `fetch_klines`, `fetch_order_book`, `fetch_tickers` через v5 API).
  * **Слой абстракции:** Базовый интерфейс `BaseExchangeAdapter` (`fetch_klines`, `fetch_order_book`, `fetch_tickers`, `subscribe_trades`, `subscribe_depth`).

### Хранилище данных
* **Реляционная БД:** SQLite (`backend/signalscript.db`) с включенным WAL-режимом (`PRAGMA journal_mode=WAL`).
  * Таблицы:
    * `user_settings` — профили параметров сканера, пороги плотностей, лимиты диска, JSON-оверрайды по монетам (`coin_overrides`).
    * `drawings` — векторные рисунки графиков (линии, лучи, горизонтальные уровни, прямоугольники, сетки Фибоначчи) с привязкой к `symbol`, `timeframe`, `user_id`.
    * `liquidations` — история принудительных ликвидаций с фиксацией `symbol`, `side`, `price`, `quantity`, `usd_amount`, `timestamp`.
    * `signals_history` — архив сработавших сигналов с нормализованными значениями метрик (`raw`, `atr_pct`, `z_score`, `percentile`).
* **Файловое хранилище (Parquet):** Директория `data/recorder/{SYMBOL}/` (настраиваемый путь и квота, по умолчанию 100 GB).
  * Формат: Apache Parquet со сжатием `snappy`.
  * Файлы:
    * `trades_YYYY-MM-DD.parquet` — сделки (`symbol`, `timestamp`, `price`, `quantity`, `usd_amount`, `is_taker_buy`, `delta`).
    * `depth_YYYY-MM-DD.parquet` — снапшоты стакана (`symbol`, `timestamp`, `bids` JSON, `asks` JSON).
  * Управление хранилищем: автоматическая FIFO-ротация при заполнении 90% квоты и удаление файлов старше `max_retention_days` (14 дней).
* **Память (In-memory buffers):**
  * Буферы сырых сделок и стакана в `recorder.py` со сбросом на диск каждые 45 секунд.
  * `footprint_cache` — агрегированные тиковые кластера свечей (до 100 свечей на фокусную монету в RAM).

## 3. Подготовка к бэктесту и реплею

### 1. Как устроена запись истории
* **Сделки (aggTrades):** WebSocket-поток `wss://fstream.binance.com/ws/{symbol}@aggTrade` слушает сделки по списку `focus_symbols` (BTC, ETH, SOL, DOGE, XRP). Тики накапливаются в оперативной памяти (`trade_buffer`) и сбрасываются каждые 45 секунд в `data/recorder/{SYMBOL}/trades_{YYYY-MM-DD}.parquet`.
* **Стакан (снапшоты):** Запрашивается срез L2 стакана (top-10) и сбрасывается в `data/recorder/{SYMBOL}/depth_{YYYY-MM-DD}.parquet`.
* **Управление объемом:**
  * Параметр `max_storage_gb` (по умолчанию 100 GB) в настройках.
  * Параметр `max_retention_days` (по умолчанию 14 дней).
  * Механизм FIFO: при превышении лимита автоматически удаляются самые старые файлы до достижения 90% от лимита.
  * Эндпоинт `GET /api/recorder/export` позволяет выгрузить Parquet-файлы в виде ZIP-архива.

### 2. Механизм перемотки / реплея
* Интерактивного тикового плеера (воспроизведение стакана и ленты в прошлом с кнопками Play / Pause / Step / Скорость 1x–10x) **на данный момент нет**.
* Имеется симулятор пакетного бэктеста (`OrderFlowBacktester` в `backend/app/services/orderflow_backtester.py`), который прогоняет исторический датасет свечей через математическую модель без визуального тикового реплея.

### 3. Контракт и схема данных для бэктестера
* **Входные данные (`BacktestRequestSchema`):**
  ```json
  {
    "symbol": "BTCUSDT",
    "timeframe": "15m",
    "days": 14,
    "strategy_type": "confluence_ema", // "confluence_ema" | "delta_absorption" | "density_bounce"
    "initial_capital": 10000.0,
    "leverage": 1.0,
    "take_profit_pct": 1.5,
    "stop_loss_pct": 0.8,
    "use_trailing": true,
    "trailing_pct": 0.5
  }
  ```
* **Моделируемые стратегии:**
  1. `confluence_ema`: пробой/отбой EMA20 при всплеске объема (`volume > MA20 * mult`) и подтверждении экстремума RSI.
  2. `delta_absorption`: поглощение лимитным ордером (аномальная дельта против движения цены).
  3. `density_bounce`: отскок от крупной плотности стакана.
* **Выходной контракт (`run_backtest`):**
  * `summary`: `initial_capital`, `final_equity`, `net_pnl`, `net_pnl_pct`, `total_trades`, `win_rate_pct`, `profit_factor`, `max_drawdown_pct`, `sharpe_ratio`.
  * `equity_curve`: массив объектов `[{ "time": ms, "equity": float, "drawdown_pct": float }]`.
  * `trades`: массив сделок `[{ "entry_time": ms, "exit_time": ms, "side": "LONG"|"SHORT", "entry_price": float, "exit_price": float, "pnl": float, "exit_reason": "TP"|"SL"|"TRAILING" }]`.

## 5. Список критических багов, узких мест и блокеров

1. **Клиентский парсинг прямого биржевого WebSocket (нагрузка на UI-поток):**
   * *Проблема:* Компонент `OrderBook.jsx` напрямую открывает WebSocket к `fstream.binance.com` на `@depth20@100ms` и `@aggTrade`.
   * *Влияние:* Во время резких движений рынка (волатильность BTC/ETH) в браузер поступает 50–100 сообщений в секунду. JSON-десериализация и пересчет агрегации уровней в основном потоке JS могут вызывать просадки FPS анимаций графика.
   * *Решение для следующих этапов:* Перенос парсинга сырых вебсокетов на бэкенд или в браузерный Web Worker, отправка на фронтенд уже нормализованных диффов с частотой 100–250 мс.
2. **Дискретность Heatmap лимитных заявок:**
   * *Проблема:* На текущем этапе плотности отображаются через векторные фигуры оверлея KLineCharts.
   * *Влияние:* При горизонтальном зуме графика плотности выглядят как отдельные фрагменты, а не как непрерывная температурная лента ликвидности.
   * *Решение для следующих этапов:* Рендеринг тепловой карты на выделенном фоновом слое Canvas/WebGL под канвасом свечей.
3. **Строгий режим React 19 (StrictMode double-mount):**
   * *Проблема:* В режиме разработки KLineCharts при быстром повторном монтировании компонента требует корректного вызова `dispose()`.
   * *Статус:* Защищено флагами инициализации `chartReady` и проверками контейнера, но при внедрении новых комплексных оверлеев требует строгого отслеживания ссылок на `chartRef`.
4. **Конкурентность записей в SQLite при аномальных всплесках:**
   * *Проблема:* Поток ликвидаций Binance (`!forceOrder@arr`) и фоновый сканер рынка пишут в одну БД SQLite.
   * *Статус:* Включен режим `WAL`, но при высокой нагрузке необходим строгий контроль коротких транзакций, чтобы предотвратить ошибку `database is locked`.
5. **Отсутствие мультибиржевой нормализации стаканов:**
   * *Проблема:* Адаптер Bybit пока работает в REST-режиме, живые стаканы агрегируются только с Binance Futures.
   * *Влияние:* Невозможно построить суммарный кросс-биржевой стакан (Binance + Bybit) в реальном времени.

## 6. Резюме готовности кодовой базы

* **Ядро ручного терминала:** Готово на **85%**. График, стакан, маркеры ликвидаций, сохранение рисунков, алерты сближения с плотностями, темы оформления и управление горячими клавишами полностью работоспособны.
* **Модуль сбора данных (Рекордер):** Готов на **90%**. Запись Parquet-файлов, лимит 100 GB, FIFO-ротация и экспорт архивов функционируют штатно.
* **Модули глубокого Order Flow анализа (Footprint, Heatmap, Реплей, Volume Profile):** Готовы на **35%**. Данные на бэкенде агрегируются и сохраняются, требуется интеграция специализированных слоев визуализации (WebGL-heatmap, встроенный в свечи Footprint и тиковый плеер реплея).
