```
Сейчас есть AGENTS.md (~23 КБ), CLAUDE.md и GEMINI.md, они будут расходиться. Codex читает AGENTS.md автоматически и обрезает слишком длинные инструкции. Сделай так:

ШАГ 3. ДОКУМЕНТЫ ДЛЯ КОНТЕКСТА (создать или обновить)
1. docs/ARCHITECTURE.md — дерево каталогов с назначением каждой папки/ключевого файла; потоки данных (откуда → куда: источники данных → engine/strategies → backend API → frontend → charts); границы модулей; внешние зависимости; конфиги и env-переменные (только имена, без значений).

Скрипт должен давать детерминированный вывод и иметь режим --check (exit code ≠ 0, если карта устарела).
3. docs/ROADMAP.md — реальная дорожная карта: Done / In progress / Next / Backlog / Known issues. У каждого пункта: id, краткое описание, затронутые файлы, приоритет, оценка сложности (S/M/L — для маршрутизации по моделям), статус. Источники: PROGRESS.md, HANDOFF.md, tasks/, твой последний вывод. 4. docs/HISTORY.md — как работали Kimi и Gemini: принятые архитектурные решения и почему (ADR-lite, по 2–4 строки), соглашения, найденные грабли, что пробовали и откатили. Это защита Codex от повторения чужих ошибок.

6. PROGRESS.md — оставь журналом, но добавь в начало 5 строк-правил: формат записи, кто и когда пишет.
7. docs/AGENT_ROUTING.md — создай заглушку с заголовками (таблица «тип задачи → роль → модель → reasoning effort», правила эскалации, бюджетные правила). Codex сам заполнит её по доступным ему моделям — НЕ придумывай за него модели.

ШАГ 4. ПРАВИЛО ПОДДЕРЖАНИЯ ДОКОВ (вписать в AGENTS.md)
Любое изменение, которое меняет структуру каталогов, публичные функции/интерфейсы, потоки данных или статус задач, обязано в том же коммите: (а) обновить docs/ARCHITECTURE.md при изменении структуры/потоков; (б) прогнать scripts/gen_codemap.py; (в) обновить статус в docs/ROADMAP.md; (г) добавить строку в PROGRESS.md. Добавь scripts/check_docs.py (или флаг --check), который это проверяет, и подключи его в существующий quality gate.

- Если нашёл секреты в отслеживаемых файлах/истории — сразу сообщи отдельным пунктом.

ШАГ 6. ПРОВЕРКИ
```

## ПРОМТ 2 — для Codex: онбординг + режим мультиагента

```
КОНТЕКСТ
Ты подключаешься к существующему проекту, который до тебя вели Kimi и Gemini (ты участвовал на ранних этапах). Репозиторий подготовлен к передаче: контекст лежит в файлах, а не в этом чате. Твоя цель — быстро довести проект до готового состояния в тех же архитектурных рамках, работая как команда, а не заново всё переоткрывая. Пользователь на подписке Codex за $20 — лимиты ограничены, поэтому главное правило: минимум токенов на единицу результата.

ПОРЯДОК ИЗУЧЕНИЯ (и ничего сверх этого, пока не потребуется задачей)
1. AGENTS.md — правила, команды, карта.
2. HANDOFF.md — состояние на сейчас и первый шаг.
3. docs/ROADMAP.md — что делать дальше.
4. docs/ARCHITECTURE.md — структура и потоки данных.
5. docs/CODEMAP.md — карта функций; код открывай ТОЛЬКО точечно по ней.
6. docs/HISTORY.md — решения и грабли Kimi/Gemini; не повторяй откаты.
7. design/ и пришедший ниже дизайн-контекст — для UI-задач.
Не сканируй репозиторий целиком, не читай .env, логи, скриншоты, .venv, node_modules. Если док противоречит коду — прав код; исправь док в том же коммите.

ШАГ 0 — НАСТРОЙ СЕБЯ (один раз, коротко)
Выясни по факту, а не по памяти: какие модели доступны тебе в /model (в моём списке: GPT-5.6 Luna/Terra/Sol, GPT-6 Luna/Astra/Sol, GPT-6.1 Terra/Sol — я не знаю их относительной цены и силы), как у тебя в этой версии устроены subagents / multi-agent, профили и skills (смотри свою документацию, --help, /status). Затем:
a) Заполни docs/AGENT_ROUTING.md: таблица «тип задачи → роль → модель → reasoning effort → когда эскалировать» на основе реальных характеристик моделей (скорость, цена, лимиты) — без догадок; что не смог проверить, пометь UNVERIFIED.
b) Настрой проектный конфиг (.codex/ или как принято в твоей версии): профили cheap / default / deep, при поддержке — кастомные субагенты (explorer, implementer, reviewer, debugger) с ограниченными правами и своими моделями.
c) Skills/плагины: используй только те, что реально нужны проекту. Ставить новые можно, но: только из доверенных источников, каждый проверь на безопасность (что делает, какие права), и учти, что описание каждого навыка стоит токенов в каждом запуске. Проверь список установленных: SwiftUI Expert, Build iOS/macOS Apps, скорее всего, нерелевантны этому проекту (Python backend + web frontend) — предложи отключить. Superpowers/Superdesign используй точечно (дизайн-ревью, сложное планирование), не как обязательную церемонию на каждую задачу.
Покажи мне итог шага 0 одним коротким сообщением и продолжай без ожидания, если я не вмешался.

РОУТЕР (правила маршрутизации; уточни в AGENT_ROUTING.md по итогам шага 0)
- Ты — оркестратор на средней модели с низким/средним reasoning. Сам пишешь только небольшие правки (≲ 30 строк, один файл). Всё остальное делегируешь.
- Поиск/разведка/чтение/сводки по коду, логам, тестам → самая дешёвая быстрая модель, возвращает ≤ 15 строк результата со ссылками file:line. Никогда не тащи сырые выводы в основной контекст.
- Реализация фичи по чёткому ТЗ из ROADMAP → средняя модель, один субагент на одну задачу, изолированный набор файлов; независимые задачи — параллельно, но не пересекаются по файлам.
- Сложный дебаг, архитектурные развилки, миграции, баги после двух неудачных попыток → самая сильная модель, высокий reasoning, ограниченный и точный контекст (задача + релевантные файлы по CODEMAP). Это редкий дорогой вызов.
- Ревью → отдельный субагент со свежим контекстом (не тот, кто писал), смотрит diff + тесты, ищет баги, регрессии, безопасность. Не придирается к мелочам.
- Эскалация: начинай с самой дешёвой модели, способной справиться; после двух провалов подряд поднимай уровень; не эскалируй из-за «неуверенности» без проваленного теста/проверки.
- Определи сложность по полю S/M/L в ROADMAP: S → дешёвая/средняя, M → средняя, L → разбей на M или планирование на сильной модели, исполнение на средней.

ЭКОНОМИЯ ТОКЕНОВ (обязательные привычки)
- Не перечитывай файлы, которые уже читал; опирайся на CODEMAP и diff. Правки — точечными патчами, не переписыванием файлов.
- Ограничивай вывод команд (head/tail, --quiet, -q, фильтры); тесты запускай сначала узко (по затронутому модулю), полный quality gate — перед коммитом.
- Одна задача — один тред; перед сменой темы сжимай контекст (/compact) или открывай новый тред с краткой выжимкой из HANDOFF.md. Не веди длинные разговоры в одном контексте.
- Планируй коротко: список из 3–7 пунктов, без эссе. Не объясняй мне очевидное.
- Перед тяжёлой операцией (параллельный fan-out, большие рефакторинги) прикинь стоимость и сделай самую дешёвую версию, дающую результат. Следи за остатком лимитов (/status) и предупреждай меня, когда осталось мало.

ПРАВИЛА РАБОТЫ В КОМАНДЕ
- Следуй соглашениям из AGENTS.md и HISTORY.md; новые соглашения не вводи без записи в доки.
- После каждой завершённой задачи, в том же коммите: gen_codemap.py, статус в ROADMAP.md, строка в PROGRESS.md, при изменении структуры — ARCHITECTURE.md; прогон quality gate. Перед завершением сессии обновляй HANDOFF.md, чтобы любой другой агент (Claude, Gemini, ты в новом треде) мог продолжить без этого чата.
- Не меняй публичные интерфейсы и структуру каталогов «заодно». Масштабные перемещения файлов — только по отдельной задаче в ROADMAP.
- Безопасность: не коммить секреты, не выводи .env, внешние сети/установки — только с явной целью.
- Критичность: если задача из ROADMAP или моя просьба кажется неверной, рискованной или есть лучший подход — скажи это ДО реализации, коротко, с предложением.

ПЕРВЫЕ ДЕЙСТВИЯ
1. Прочитай файлы по порядку изучения. 2. Выполни шаг 0. 3. Возьми из HANDOFF.md «первый шаг» и выполни его по роутеру. 4. Дальше иди по ROADMAP сверху вниз по приоритету, пока я не дам другой курс. Дизайн-контекст и мои пожелания по UI придут отдельным блоком ниже — для UI-задач они приоритетнее общих умолчаний.

ФОРМАТ ТВОИХ ОТЧЁТОВ МНЕ
Коротко и по делу: что сделано (результат, а не процесс), что проверено (тесты/гейт — фактические результаты), риски/вопросы, следующий шаг. Без пересказа действий.
```
